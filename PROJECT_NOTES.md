## Arquitectura base aceptada

- pnpm + Turborepo;
- TypeScript;
- NestJS + REST/OpenAPI como frontera de aplicación y única ruta de escrituras críticas;
- Supabase Auth + PostgreSQL administrado; Storage cuando el módulo defina políticas;
- migraciones SQL versionadas de Supabase como autoridad única del schema;
- ORM, cola y transporte Realtime todavía pendientes; Realtime nunca sustituye recuperación durable por cursor;
- Next.js;
- Expo/React Native;
- React para KDS;
- packages/domain para lógica pura;
- packages/shared-types;
- packages/sync-engine;
- adaptadores para pagos, PAC, impresión y terceros.

Esta es la alternativa B aceptada por ADR-010 y delimitada por ADR-001. Data API directa solo puede servir lecturas RLS/CRUD no financiero expresamente permitido; no existe una segunda ruta para escrituras críticas.

- `apps/api` usa configuración fail-closed de Auth y PostgreSQL, `auth.getUser(token)`, identidad derivada/congelada, `APP_GUARD` global y scope UUID exacto. Solo `/api/v1/health` es público; `/api/v1/session` exige identidad y `POST /api/v1/access/branch` revalida membresía efectiva mediante una función PostgreSQL privada y devuelve 403 genérico ante cualquier rechazo.
- La URL runtime PostgreSQL solo acepta el rol dedicado `app_api` ligado al mismo project ref, TLS `verify-full`, CA vigente y host directo/Supavisor autorizado. `postgres`, parámetros de conexión inesperados y CA inválida se rechazan. Nest no recibe grants de tablas: `app_api` solo puede ejecutar el lookup privado.
- La migración productiva inicial vive en `supabase/migrations`, separada del spike. Modela Restaurant/Branch activos, membresías exactas históricas y múltiples roles históricos; usa FK compuesta, índices parciales, RLS+FORCE RLS, helpers caller-bound y grants de lectura explícitos. `app_private`/`app_rls` no se exponen. ADR-002 mantiene esta frontera como propuesta hasta evidencia PostgreSQL real.
- Las funciones `SECURITY DEFINER` quedan explícitamente en propiedad de `postgres` y la migración aborta si ese owner no tiene `BYPASSRLS`. `app_api` nace `NOLOGIN`, sin contraseña ni privilegios elevados; una colisión aborta. PostgreSQL 16 concede obligatoriamente a su creador no-superusuario una fila ADMIN con grantor bootstrap: en Supabase es `app_api` → `postgres`, otorgada por `supabase_admin`, sin INHERIT ni SET. Las auditorías aceptan solo esa relación inerte y rechazan cualquier otra. Su aprovisionamiento privado posterior está documentado y exige prueba de mínimos privilegios.
- Cuarenta y dos pruebas de API cubren configuración Auth/DB, principal, autorización, adapter hostil-resistente, contratos de migración/config, verificador transaccional y smoke Nest 200/401/403. El verificador fresh aplica migración+catálogo dentro de una transacción y siempre revierte; su CLI y la del E2E solo emiten códigos sanitizados.
- El runner remoto de tenancy crea usuarios desechables y fixtures 2×2, comprueba Data API para anon/authenticated/service role, conexión mínima `app_api`, Nest real, false pairs, constraints y revocación con el mismo token, y limpia en orden FK-safe. La auditoría pre-provisioning exige `NOLOGIN`; la auditoría runtime exige el `LOGIN` necesario y conserva todos los demás mínimos. La recuperación standalone exige UUID y confirmación repetida, opt-in propio, mismo advisory lock, metadata/email exactos, grafo 2×2 completo o Auth-only y deletes por IDs con `RETURNING`; aborta ante estados parciales o contaminados.
- La contraseña administrativa comprometida fue rotada sin publicarla. La nueva credencial conectó por el pooler al proyecto exacto `zwbyiefqeujstyzysydn` usando la CA local y TLS `verify-full`. Tras demostrar primero rollback seguro, Emmanuel autorizó la aplicación persistente de `20260830000100`: quedó como sexta migración remota, sin seeds/roles/Vault/config push adicionales. La auditoría posterior confirmó 5 políticas, 5 tablas RLS+FORCE RLS y 4 funciones `SECURITY DEFINER`; `db lint` quedó sin errores.
- La evidencia remota detectó dos incompatibilidades antes de aplicar: el `postgres` administrado no es superusuario, y `pg` devuelve un arreglo de resultados para SQL multi-statement. La migración evita ALTERs reservados, audita la concesión ADMIN obligatoria de PostgreSQL 16 sin relajar otras membresías, y el verificador normaliza resultados únicos/múltiples. CodeGraph quedó actualizado en 84 archivos, 1,825 nodos y 7,255 relaciones; `runSchemaVerification` continúa limitado a su CLI y pruebas.
- El historial del ref aislado contiene exactamente las versiones `20260825000100` a `20260830000100`; las primeras cinco pertenecen al spike y la sexta es `20260830000100_create_tenancy_memberships.sql`, primera migración productiva.

No se reparó historial ni cambió el enlace.

El entrypoint destructivo solo consume configuración administrativa y el recovery; comparte marcadores/lock con el runner y no es alcanzable por controladores o clientes. Sus cinco pruebas de recuperación y tres de configuración elevan la suite API a 50 casos locales.

Valida proyecto/host/CA/TLS y contraseña sin imprimirla, fija SCRAM, toma un advisory lock global, concede `LOGIN` con expiración de diez minutos, prueba una conexión nueva y sus permisos permitidos/denegados, audita el estado runtime y solo entonces promueve la credencial a vigencia indefinida. CodeGraph no estuvo disponible para la reconsulta de este corte; la inspección manual dirigida confirmó que los CLI son los únicos consumidores de aprovisionamiento/recovery, el lock se comparte con el runner E2E y no existe referencia desde controladores o clientes.

Acepta estado temporal, expirado, runtime o ya deshabilitado solo con fingerprint de rol exacto; confirma primero `NOLOGIN PASSWORD NULL`, después termina sesiones en hasta tres barridos y exige desde una conexión nueva el mismo OID, cero sesiones y la auditoría pre-provisioning fijada por hash. Un commit ambiguo se reconcilia y como máximo se repite una vez.
