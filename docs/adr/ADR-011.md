# ADR-011: transporte Realtime recuperable para POS y KDS

- Estado: **ACEPTADA — autorizada por Emmanuel**
- Fecha: 2026-09-02
- Decisiones relacionadas: [ADR-001](./ADR-001.md), [ADR-010](./ADR-010.md)

## Contexto

Fase 1 necesita avisar cambios de órdenes a web y KDS con baja latencia. El aviso
no puede convertirse en autoridad: PostgreSQL conserva el estado durable y cada
cliente debe poder reconstruirlo mediante una lectura incremental con cursor.
También deben mantenerse la validación de Supabase Auth, el aislamiento por
Restaurant/Branch, el filtro por estación y la revocación de membresías.

ADR-001 dejó pendiente elegir entre Supabase Broadcast, Postgres Changes y un
gateway controlado por NestJS. El repositorio ya concentra autenticación,
autorización RBAC y acceso PostgreSQL privado en `apps/api`; todavía no existe
persistencia productiva de Order ni un cursor KDS durable.

## Opciones evaluadas

### A. Socket.IO en el NestJS existente — recomendada

- Reutiliza la frontera de autenticación y `MembershipAuthorizationService`.
- Permite autorizar explícitamente `orders.read`/`kds.read`, Branch y estación
  antes de unir un socket a una sala.
- Mantiene las escrituras de negocio exclusivamente en REST/NestJS.
- Nest soporta oficialmente Socket.IO mediante `@nestjs/websockets` y
  `@nestjs/platform-socket.io`.
- Requiere una decisión adicional de adapter/backplane antes de ejecutar más de
  una réplica API. El piloto de Fase 1 queda limitado a una sola réplica.

### B. Supabase Broadcast privado

- Reduce infraestructura propia y Supabase lo recomienda frente a Postgres
  Changes cuando importan escalabilidad y seguridad.
- Introduce autorización adicional mediante RLS sobre `realtime.messages` y
  configuración remota de canales privados.
- La política se cachea durante la conexión; una revocación exige refrescar el
  JWT o desconectar el canal de forma coordinada.
- Duplica parte del límite de autorización que hoy pertenece a NestJS y exige
  cambios remotos separados antes de poder demostrar el flujo real.

### C. Supabase Postgres Changes

- Es la opción de menor código para observar filas.
- Acopla clientes a cambios físicos del esquema y procesa autorización por
  evento y suscriptor; Supabase documenta que escala con los suscriptores y que
  preserva orden en un solo hilo.
- No ofrece una frontera de evento de dominio y no sustituye el cursor durable.

## Decisión propuesta

Adoptar **Socket.IO sobre WebSocket en el mismo servidor NestJS**, con namespace
versionado `/realtime/v1`, únicamente para notificaciones. Durante Fase 1 se
ejecutará una sola réplica API; desplegar varias réplicas requiere otra decisión
sobre backplane y pruebas de entrega/recuperación.

El contrato tendrá estos límites:

- el access token viaja en `auth`, nunca en query string, URL o logs;
- la conexión verifica el token con el puerto de autenticación existente;
- una suscripción incluye Restaurant, Branch y estación, se valida de forma
  fail-closed y exige `kds.read` o `orders.read` según el canal;
- el servidor revalida la membresía antes de suscribir y antes de emitir a una
  conexión; una revocación desconecta o excluye inmediatamente al socket;
- el cliente no puede crear/modificar órdenes, pagos, caja ni transiciones por
  el socket; esas mutaciones continúan por REST versionado;
- la notificación contiene solo identidad/versiones/cursor y obliga al cliente
  a leer el estado durable; no transporta un agregado financiero autoritativo;
- conectar, reconectar, detectar un salto de cursor o recibir un evento obliga
  a recuperar mediante un endpoint REST incremental y scopeado;
- límites de payload, rate limit de suscripción, heartbeat, backpressure y logs
  sin secretos forman parte de la implementación mínima.

## Orden de implementación propuesto

1. Crear contratos compartidos exactos para notificación, suscripción y cursor.
2. Implementar persistencia productiva de Order + eventos KDS y un endpoint REST
   de recuperación incremental por cursor.
3. Añadir el gateway autenticado y las salas derivadas exclusivamente del scope
   autorizado.
4. Emitir una notificación después del commit durable, nunca antes.
5. Probar pérdida intencional, reconexión, revocación, estación incorrecta,
   Branch/Restaurant cruzados, payload hostil y cero bypass de escritura.
6. Integrar el KDS mínimo y verificar el flujo real en navegador.

## Criterios de aceptación

- conexión anónima, token inválido o payload hostil: rechazada sin filtrar datos;
- `kds.read` ausente, Branch falso, otro Restaurant u otra estación: cero eventos;
- revocación con token todavía vivo: el socket deja de recibir;
- una notificación omitida deliberadamente se recupera por cursor y produce el
  mismo estado autoritativo;
- reintentos/reconexiones no duplican transiciones de negocio;
- ninguna mutación sensible es alcanzable por mensajes entrantes;
- consola/red y desconexión/reconexión se verifican en KDS real;
- lint, typecheck, pruebas, build y CodeGraph quedan verdes.

## Consecuencias

- Se añade Socket.IO a la API y a los clientes que consuman Realtime.
- El gateway no se implementará antes del cursor durable: emitir sin recuperación
  violaría ADR-001 aunque la conexión WebSocket funcionara.
- La primera versión no promete fan-out multi-réplica ni operación LAN/offline.
- Supabase Broadcast y Postgres Changes quedan rechazados para este slice, no
  prohibidos para otros casos futuros aprobados mediante ADR.
