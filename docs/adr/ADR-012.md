# ADR-012: cola durable para jobs e integraciones de v1.0

- Estado: **ACEPTADA — autorizada por Emmanuel**
- Fecha: 2026-09-04
- Decisiones relacionadas: [ADR-001](./ADR-001.md), [ADR-010](./ADR-010.md), [ADR-011](./ADR-011.md)

## Contexto

La arquitectura híbrida ubica jobs e integraciones en NestJS, pero no eligió una
cola. El repositorio tampoco contiene hoy un worker, una dependencia de cola ni
un workload externo que deba ejecutarse en segundo plano. Socket.IO ya resuelve
las notificaciones de baja latencia del POS/KDS bajo ADR-011 y la recuperación
durable por cursor hace innecesario convertir Realtime en una cola.

v1.0 sí necesita una decisión antes de incorporar efectos externos recuperables,
por ejemplo push, email, webhooks o, en una versión posterior, CFDI. La solución
debe preservar el aislamiento Restaurant/Branch, permitir enqueue atómico con la
transacción que origina el trabajo, sobrevivir reinicios y no duplicar efectos.

## Opciones evaluadas

### A. Supabase Queues/PGMQ privado, consumido por NestJS — recomendada

- Reutiliza el PostgreSQL administrado ya seleccionado y evita otro proveedor en
  v1.0.
- Proporciona mensajes durables, visibility timeout y archivo mediante `pgmq`.
- Permite encolar dentro de la misma transacción PostgreSQL que persiste el
  cambio de negocio.
- Requiere habilitar la extensión, crear las colas mediante migración SQL
  versionada y operar un proceso worker de NestJS.
- Comparte capacidad y conexiones con la base transaccional; exige límites,
  métricas y una salida futura si la carga afecta al POS.

### B. BullMQ sobre Redis administrado

- Tiene integración oficial con NestJS, workers distribuidos y un ecosistema
  amplio para reintentos, prioridades y observabilidad.
- Agrega proveedor, credenciales, red, respaldo, costo y operación de Redis antes
  de existir un workload que lo justifique.
- El enqueue no comparte de forma nativa la transacción PostgreSQL de negocio;
  necesitaría transactional outbox para evitar la ventana commit/publicación.

### C. Tabla outbox y poller propios

- Mantiene atomicidad y no agrega infraestructura.
- Obliga al proyecto a construir y mantener leasing, visibility timeout,
  concurrencia, backoff, archivo, reaper y observabilidad ya cubiertos por una
  cola PostgreSQL mantenida.

### D. Promesas o timers dentro del proceso HTTP

- No agrega infraestructura.
- Pierde trabajos en reinicios y no ofrece recuperación durable, control de
  concurrencia ni entrega demostrable; se rechaza para cualquier efecto externo.

## Decisión propuesta

Adoptar **Supabase Queues sobre PGMQ** como cola durable de v1.0 cuando aparezca
el primer workload asíncrono aprobado. La cola será infraestructura privada de
servidor:

- solo NestJS produce y consume mediante la conexión PostgreSQL privada;
- `pgmq` y sus funciones no se exponen mediante Data API, y web/mobile/KDS no
  reciben permisos de cola;
- la extensión y cada cola se crean exclusivamente en una migración SQL nueva,
  reproducible y autorizada; no se configuran manualmente en Dashboard;
- se usan colas básicas con tablas logged; las colas unlogged no son válidas
  para efectos recuperables;
- el mensaje lleva un envelope versionado con `jobId`, `jobType`,
  `idempotencyKey`, `correlationId`, `restaurantId`, `branchId` cuando aplique,
  referencia al evento/entidad origen, `occurredAt` del servidor y payload
  mínimo validado;
- el payload no contiene secretos, tokens, PAN/CVV, certificados, llaves
  privadas ni datos personales completos; el worker recupera lo estrictamente
  necesario desde la fuente autorizada;
- enqueue y cambio de negocio comparten transacción cuando el job deriva de una
  mutación; un rollback deja ambos ausentes;
- la entrega de la cola no sustituye la idempotencia del efecto: cada adaptador
  externo usa una clave estable y persiste su resultado antes de reconocer el
  mensaje;
- los fallos usan backoff acotado, máximo explícito de intentos y archivo/dead
  letter observable; estados financieros ambiguos nunca se reintentan a ciegas;
- un worker NestJS separado del proceso HTTP consume los jobs y admite apagado
  ordenado; no se inicia un worker embebido por réplica API;
- métricas mínimas: profundidad, edad del mensaje más antiguo, intentos, éxitos,
  fallos, archivo/dead letter, duración y estado del worker, siempre con scope y
  correlationId cuando sea seguro;
- una prueba periódica de respaldo/restauración incluye las colas logged y sus
  mensajes pendientes.

La aprobación de esta ADR no habilita `pgmq`, no crea colas, no aplica
migraciones y no selecciona un proveedor de push, email, pagos o CFDI. La
implementación comienza únicamente con un workload concreto y otra revisión del
modelo de datos, capacidad y destino.

## Realtime y escalamiento

ADR-011 permanece sin cambios: Socket.IO solo notifica y REST/cursor recupera el
estado durable. v1.0 conserva una sola réplica API. PGMQ no funciona como
backplane de Socket.IO. Antes de desplegar varias réplicas se requiere una ADR
separada para el adapter/backplane y pruebas de revocación, fan-out, pérdida y
recuperación por cursor.

## Criterios de aceptación para la futura implementación

1. Una base vacía y una base en la versión anterior crean la extensión/cola por
   la misma migración versionada; rollback y restore están documentados.
2. Data API no expone `pgmq`/wrappers y los roles cliente tienen cero grants.
3. Enqueue + mutación es atómico; un fallo inducido deja cero mensaje huérfano.
4. Dos workers concurrentes no ejecutan simultáneamente el mismo lease.
5. Un crash antes del ack vuelve a entregar el mensaje después del visibility
   timeout y el adaptador idempotente produce un solo efecto.
6. Payloads hostiles, versión desconocida y scope falso se archivan/rechazan sin
   efecto ni fuga entre tenants.
7. Agotar intentos produce una dead letter visible y recuperable mediante una
   operación administrativa auditada, nunca un bucle infinito.
8. Lint, typecheck, unit/integration/contract tests, build y CodeGraph quedan
   verdes; la verificación PostgreSQL es rollback-only antes de solicitar apply.

## Disparadores para reevaluar Redis/BullMQ

- la cola compite de forma medible con la carga transaccional del POS;
- el volumen o latencia objetivo no cabe dentro del presupuesto PostgreSQL;
- se necesitan prioridades, workflows o fan-out que PGMQ no resuelve de forma
  mantenible;
- múltiples servicios necesitan una cola independiente de PostgreSQL;
- los ejercicios de recuperación o disponibilidad muestran que compartir el
  dominio de fallo es inaceptable.
