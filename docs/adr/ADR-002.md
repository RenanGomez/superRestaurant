# ADR-002: Restaurant/Branch como frontera de aislamiento

- Estado: **PROPUESTA — implementación inicial local**
- Fecha: 2026-08-29
- Decisión habilitante: [ADR-001](./ADR-001.md)

## Contexto

Una misma identidad puede operar en varios restaurantes y sucursales con
roles distintos. El alcance no puede inferirse del cliente ni ampliarse desde
Restaurant hacia todas sus Branches: eso permitiría fugas entre operaciones.
También debe conservarse el historial de altas, roles y revocaciones.

## Propuesta

- Restaurant es el tenant principal y Branch el alcance operativo exacto.
- Cada membresía pertenece a `actor + Restaurant + Branch`; no existe una
  sucursal implícita ni herencia automática de owner/admin.
- Una membresía admite varios roles simultáneos. Membresías y concesiones de
  roles revocadas son históricas e inmutables; reactivar crea una fila nueva.
- Los nueve códigos iniciales son `owner`, `admin`, `manager`, `supervisor`,
  `cashier`, `waiter`, `kitchen`, `viewer` y `auditor`. La matriz precisa de
  permisos e inheritance permanece pendiente y debe versionarse aparte.
- La Data API no permite escrituras en estas tablas. Sus lecturas requieren
  JWT autenticado, grants explícitos y RLS caller-bound.
- NestJS usa una función privada parametrizada con la identidad verificada y
  el scope UUID exacto. El DTO nunca aporta un actor confiable.
- Una autorización HTTP no basta para una escritura crítica: Order, Payment,
  Refund y CashMovement deberán revalidar membresía/rol dentro de la misma
  transacción y coordinarse con la revocación para cerrar carreras TOCTOU.
- Las FK usan `RESTRICT`; ninguna baja elimina historia por cascada.

## Consecuencias

- Revocar una membresía o un rol deja de autorizar lecturas y futuras
  operaciones con el mismo access token, sin esperar a que expire.
- Agregar una Branch no concede acceso a nadie automáticamente.
- La gestión de invitaciones, perfiles, roles personalizados, permisos por
  acción e interfaz administrativa queda fuera de este primer slice.
- La migración productiva vive solo en `supabase/migrations`; no reutiliza el
  schema del spike ni crea una historia Prisma paralela.

## Verificación exigida antes de aceptar

- matriz real 2×2 con dos usuarios, dos restaurantes y dos sucursales por
  restaurante;
- revocación de membresía y de un único rol usando el mismo token;
- RLS de lectura y rechazo de toda escritura Data API, incluidos anon y
  service role sin grants de negocio;
- constraints de scope cruzado, duplicados activos, rol inválido, evidencia de
  revocación incompleta y borrado de usuarios referenciados;
- carrera entre revocación y una futura escritura crítica;
- migración desde base vacía, upgrade y auditoría de catálogo/grants/policies.
