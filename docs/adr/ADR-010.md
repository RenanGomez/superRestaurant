# ADR-010: boundary for Auth, persistence, and realtime

- Status: **PROPOSED — spike IN_PROGRESS**
- Date: 2026-08-25
- Decision owners: human project owner after evidence review
- Timebox: 4 business days; hard stop at the end of Day 5

## Context

The POS needs auditable tenant isolation, atomic critical writes, idempotency, revocable authorization, recoverable KDS realtime, reproducible migrations, backup/restore, and secret boundaries. ADR-001 remains blocked until this ADR is accepted.

The candidates are:

- **A**: project-managed NestJS + Prisma + PostgreSQL + Redis/BullMQ + Socket.IO.
- **B**: Supabase PostgreSQL/Auth/Storage with NestJS as the only critical-write boundary.
- **C**: direct Supabase Data API/RPC, limited to non-financial reads or explicitly permitted CRUD.

No option is selected by this document today. Option C cannot be the principal core backend without an explicit change to the domain-package rule and ADR-003.

## Current evidence

Day 1 delivered the reusable harness in `spikes/adr-010`. It contains deterministic fixtures for two restaurants and two branches each, the shared gate contract, a strict in-memory control adapter, and induced-fault tests. The control adapter is not evidence for A/B/C, does not score any option, and does not demonstrate real persistence. Its single-write-frontier result is explicitly `requires-human-inspection`, never an automated pass.

Option A now has a PostgreSQL-backed `Adr010Adapter`, an isolated migration, a Nest boundary and an opt-in gate runner under `options/a-own-stack`. Its restore rejects backup-controlled identifiers, non-empty destinations and conflicts. PostgreSQL was not available, so only preflights ran. Moreover `issueSession` is a test double rather than login/refresh/Auth; the runner therefore always reports `eligibleForAdr010Go: false` and exits non-zero even if database checks pass.

Option B now implements the common adapter under `options/b-supabase-nest`. Nest verifies access tokens through the official `auth.getUser(token)` call, derives actors and refund supervisors only from verified users, and invokes Order/Payment/Refund/CashMovement functions over a private PostgreSQL connection. `adr010_b` is the sole exposed schema and contains RLS-protected read tables; every privileged function lives in unexposed `adr010_b_private`, with empty `search_path` and no Data API-role execution grants. Against the isolated project `ndblkcmdgpxsxylacutx`, five migrations, catalog audit 27/27, database lint, authenticated RLS, refresh rotation/revocation and 15 remote capabilities passed with clean teardown. B remains ineligible for scoring until the human write-frontier inspection and a complete five-migration push against another fresh project/CI close gates 4 and 7; physical recovery remains separate operational evidence.

Option C has a publishable-key-only direct client limited to scoped order and KDS reads plus SQL that revokes generic writes. It deliberately exposes no critical mutation or `Adr010Adapter` and is NO-GO as the principal backend. Its shared RLS/read infrastructure received remote evidence through option B, but C still does not implement or pass the complete common adapter gates and remains limited to non-financial reads.

## Required evidence before a decision

Each candidate must implement the common adapter contract and pass the following evidence gates before it can receive a 0–5 score. Gates 1–3 and 5–10 are executable; gate 4 is a mandatory human inspection with documented, runnable evidence. A self-reported list of paths cannot pass gate 4.

1. Isolation: zero cross-restaurant or cross-branch reads/writes; rejected writes leave no target-scope artifact.
2. Transaction: order + lines + snapshots + audit is atomic; induced failure leaves exact artifact IDs unchanged.
3. Idempotency: 20 concurrent re-sends return and persist exactly one business result for the idempotency key.
4. Single write frontier: exactly one authorized path for Order, Payment, and CashMovement, verified by human inspection of the option's documented runnable evidence.
5. Realtime recovery: after a deliberately omitted KDS delivery, a scoped cursor read recovers the event and does not leak it across restaurant/branch.
6. Auth/scope: login membership scope is enforced and revocation is revalidated immediately before the critical write.
7. Migration: migration from empty yields the thin slice, and a rerun preserves order/line/snapshot/audit counts and IDs.
8. Backup/restore: the spike dataset restores the same order/line/snapshot/audit counts and identifiers.
9. Secrets: no privileged credential reaches web/mobile; only the Supabase URL and publishable-key names are client-safe. Secret, legacy `anon`, legacy `service_role`, database, private-key and token names are rejected.
10. Reproducibility: evidence names `pnpm-lock.yaml`, all frozen commands in the spike README, and a stable command-output location.

Only then it can receive a 0–5 score in each weighted criterion. Weighted score is `sum((score / 5) × weight)`. GO requires every gate, every criterion minimum, and at least 75/100.

| Criterion | Weight | Minimum |
| --- | ---: | ---: |
| Security and isolation | 25 | 4/5 |
| Transactional domain and single frontier | 25 | 4/5 |
| Future offline compatibility | 15 | 3/5 |
| Operations, backup, observability | 15 | 3/5 |
| Productivity/maintainability | 10 | 3/5 |
| Cost and portability | 10 | 3/5 |

A score, recommendation, or GO/NO-GO is intentionally absent until that evidence exists.

For B/C, an external Supabase project and server-side secret configuration are required for the real evaluation. Use `ADR010_SUPABASE_PUBLISHABLE_KEY` only for later client/RLS checks and `ADR010_SUPABASE_SECRET_KEY` only in server/CI secret storage for Supabase Auth Admin/bootstrap. B's critical adapter uses `ADR010_DATABASE_URL`, a server-only PostgreSQL connection, to invoke a private SQL function; it does not send a critical write through Supabase Data API. The isolated `adr010_b` schema must be explicitly exposed through the Data API only for its RLS-protected reads. Its `adr010_b_private` schema holds every `SECURITY DEFINER`/administrative function, is never exposed, revokes `PUBLIC` and Data API-role execution, and uses an empty `search_path` with fully qualified object access. Legacy `anon` and `service_role` JWT keys are deprecated by Supabase by the end of 2026 and are not selected for new configuration; the database role name remains relevant only when proving that the Data API has no generic writes or private function execution.

## Consequences until resolved

- `packages/domain` and shared neutral contracts can proceed.
- Definitive Auth, Prisma/persistence, RLS, direct client data access, and production realtime remain blocked.
- If no option passes by the hard stop, this ADR becomes BLOCKED with the precise failed evidence; neutral domain work continues.
