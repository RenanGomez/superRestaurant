# ADR-001: arquitectura inicial híbrida Supabase + NestJS

- Estado: **ACEPTADA — autorizada por Emmanuel**
- Fecha: 2026-08-29
- Decisión habilitante: [ADR-010](./ADR-010.md)

## Contexto

El POS necesita identidad revocable, aislamiento por Restaurant/Branch,
persistencia transaccional, idempotencia, auditoría y recuperación de KDS sin
dispersar reglas críticas entre clientes, API y base de datos. ADR-010 comparó
un stack propio, una opción híbrida y acceso directo a Supabase. La opción B
demostró los diez gates, obtuvo 75/100 y fue aprobada expresamente por Emmanuel
el 2026-08-29.

## Decisión

Adoptar una arquitectura híbrida con estos límites:

- **Supabase administrado** provee PostgreSQL y Auth. Supabase Storage es el
  proveedor seleccionado cuando un módulo necesite objetos, pero sus buckets,
  políticas y datos permitidos deben decidirse en ese módulo.
- **NestJS** es la frontera de aplicación obligatoria para toda escritura
  crítica o sensible, incluidas Order, Payment, Refund y CashMovement. Web,
  Mobile y KDS no acceden a PostgreSQL ni invocan una escritura crítica por
  Data API/RPC.
- NestJS valida el access token con Supabase Auth, deriva la identidad del
  usuario verificado y revalida membresía, rol, Restaurant y Branch antes de
  confirmar la mutación. Los clientes no envían un `actorId` confiable.
- Las escrituras críticas llegan por una conexión PostgreSQL privada de
  servidor con TLS `verify-full` y ejecutan una única frontera transaccional.
  RLS es defensa en profundidad y no sustituye la autorización ni las
  invariantes del dominio.
- La Data API puede usarse desde clientes solo para lecturas expresamente
  permitidas, acotadas por RLS y cubiertas por pruebas de fuga entre tenants.
  Cualquier CRUD no crítico directo requiere una allowlist documentada; no se
  habilitan escrituras genéricas.
- Las migraciones SQL versionadas aplicadas por el flujo de Supabase son la
  única autoridad del esquema PostgreSQL, políticas RLS, grants y funciones.
  Prisma no puede crear una segunda historia de migraciones; su posible uso
  futuro como cliente o generador de tipos requiere una decisión acotada y no
  puede sustituir las entidades de `packages/domain`.
- Realtime solo notifica. El estado durable y autoritativo permanece en
  PostgreSQL, y todo consumidor debe recuperarse mediante lectura/cursor
  versionado después de una entrega perdida o reconexión. ADR-010 no eligió
  entre Supabase Broadcast, Postgres Changes o Socket.IO.
- Jobs e integraciones pertenecen a NestJS y no son autoridad de órdenes,
  pagos, caja ni eventos auditables. ADR-010 no eligió Redis/BullMQ ni otra
  implementación de colas.
- `packages/domain` permanece puro y sin dependencias de NestJS, Supabase,
  ORM, red o UI.

## Componentes no reutilizables directamente

Los schemas `adr010_b` y `adr010_b_private`, sus fixtures y los hooks de fallo
pertenecen al spike. No son el esquema productivo. La implementación real debe
crear nombres, migraciones y contratos de producto, conservando las
invariantes demostradas y repitiendo la inspección de frontera cuando existan
controladores y bundles reales.

El prototipo histórico sigue sujeto a ADR-006 y no aporta código reutilizable
sin licencia o autorización escrita.

## Consecuencias

- Quedan desbloqueadas la implementación definitiva de `apps/api`, Auth,
  persistencia, RLS, login y Realtime bajo esta frontera.
- La opción A no se adopta como arquitectura principal y la opción C queda
  limitada a lecturas o CRUD no financiero expresamente autorizado.
- La aplicación asume acoplamiento consciente a Supabase Auth, RLS,
  configuración de schemas y Realtime. PostgreSQL, migraciones versionadas y
  exportación lógica preservan una vía parcial de portabilidad.
- El resultado de 75/100 no deja margen: antes de producción siguen siendo
  obligatorios recuperación física, RPO/RTO medidos, observabilidad, alertas,
  pruebas de carga/costo y un ejercicio de salida del proveedor.
- Cada nuevo flujo financiero debe probar aislamiento, atomicidad,
  idempotencia, revocación y ausencia de un bypass de escritura.

## Pendientes de implementación

- Diseñar el esquema de producto desde sus invariantes; no traducir el spike
  mecánicamente.
- Crear `apps/api` y el adaptador Auth/productivo con DTOs mínimos y secretos
  solo de servidor.
- Definir la matriz RBAC y el contrato de sesiones/selección de alcance.
- Elegir y verificar el transporte Realtime en el flujo KDS real, conservando
  la recuperación por cursor como requisito independiente del transporte.
- Definir despliegue, jobs, observabilidad y recuperación física antes del
  piloto/producción.
